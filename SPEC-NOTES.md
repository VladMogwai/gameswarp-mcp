# MCP 2025-11-25 — выжимка для написания сервера

Версия **2025-11-25** — та, которую реализует установленный SDK 1.30.0.
Взято с modelcontextprotocol.io, сокращено до того, что нужно для stdio-сервера
с инструментами. Ресурсы, промпты, HTTP-транспорт, авторизация — опущены.

## 1. Транспорт stdio

- Клиент запускает сервер **дочерним процессом**.
- Сервер читает JSON-RPC из `stdin`, пишет в `stdout`.
- Сообщения разделяются переводом строки и **НЕ ДОЛЖНЫ содержать переводов строк
  внутри**. `JSON.stringify` без отступов это гарантирует; красивое форматирование
  сломает протокол.
- Кодировка — **UTF-8**.
- Сервер **НЕ ДОЛЖЕН** писать в `stdout` ничего, кроме валидных MCP-сообщений.
- Сервер **МОЖЕТ** писать что угодно в `stderr` — логи, отладку, ошибки.
  Клиент не обязан считать вывод в `stderr` признаком ошибки.
- Завершение: клиент закрывает `stdin`, ждёт выхода, потом `SIGTERM`, потом `SIGKILL`.

## 2. Хендшейк

Три сообщения, строго в этом порядке.

**1. Клиент → сервер: `initialize`**

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-11-25",
    "capabilities": { "roots": { "listChanged": true }, "sampling": {} },
    "clientInfo": { "name": "ExampleClient", "version": "1.0.0" }
  }
}
```

**2. Сервер → клиент: ответ со своими возможностями**

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-11-25",
    "capabilities": { "tools": { "listChanged": true } },
    "serverInfo": { "name": "gameswarp", "version": "0.1.0" },
    "instructions": "Необязательная подсказка клиенту"
  }
}
```

**3. Клиент → сервер: уведомление о готовности**

```json
{ "jsonrpc": "2.0", "method": "notifications/initialized" }
```

Правила:
- До ответа на `initialize` клиент не шлёт ничего, кроме `ping`.
- До получения `initialized` сервер не шлёт ничего, кроме `ping` и логов.
- Если сервер не поддерживает запрошенную версию — отвечает своей последней.
  Если клиента она не устраивает, он отключается.

Поле `instructions` — недооценённое место: туда можно положить общую подсказку,
как пользоваться сервером в целом, а не отдельным инструментом.

## 3. Объявление возможностей

Сервер с инструментами **ОБЯЗАН** объявить:

```json
{ "capabilities": { "tools": { "listChanged": true } } }
```

`listChanged` — будет ли сервер уведомлять об изменении списка инструментов.
Если список статичен, ставь `false` и не думай об этом.

## 4. Список инструментов

**Запрос** — `tools/list`, поддерживает постраничность через `cursor`.

**Ответ:**

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "tools": [
      {
        "name": "get_weather",
        "title": "Weather Information Provider",
        "description": "Get current weather information for a location",
        "inputSchema": {
          "type": "object",
          "properties": {
            "location": { "type": "string", "description": "City name or zip code" }
          },
          "required": ["location"]
        }
      }
    ]
  }
}
```

### Поля инструмента

| Поле | Обяз. | Что это |
|---|---|---|
| `name` | да | идентификатор |
| `title` | нет | человекочитаемое имя для интерфейса |
| `description` | нет по спеке, **да по факту** | единственное, по чему модель решает, звать ли |
| `inputSchema` | да | JSON Schema аргументов |
| `outputSchema` | нет | JSON Schema результата |
| `annotations` | нет | подсказки о поведении; клиент считает их недоверенными |

### Имена

1–128 символов, только `A-Z a-z 0-9 _ - .`, без пробелов и запятых,
регистрозависимые, уникальные внутри сервера.

### inputSchema

**ОБЯЗАН** быть валидным объектом JSON Schema, **никогда не `null`**.
По умолчанию диалект 2020-12.

Инструмент без аргументов:

```json
{ "type": "object", "additionalProperties": false }
```

## 5. Вызов инструмента

**Запрос:**

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": { "name": "get_weather", "arguments": { "location": "New York" } }
}
```

**Ответ:**

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "result": {
    "content": [
      { "type": "text", "text": "Current weather in New York:\nTemperature: 72°F" }
    ],
    "isError": false
  }
}
```

`content` — массив, элементы могут быть разных типов: `text`, `image`, `audio`,
`resource_link`, `resource`. Для нашего проекта нужен только `text`.

### Структурированный результат

Если хочешь отдавать данные, а не прозу, — поле `structuredContent`:

```json
{
  "result": {
    "content": [{ "type": "text", "text": "{\"temperature\": 22.5}" }],
    "structuredContent": { "temperature": 22.5, "conditions": "Partly cloudy" }
  }
}
```

Для совместимости тот же JSON **СЛЕДУЕТ** продублировать текстом в `content`.
Если объявил `outputSchema` — результат **ОБЯЗАН** ему соответствовать.

`structuredContent` — это данные, которые вернул сервер. К «структурированному
выводу» модели (генерации по схеме) отношения не имеет, несмотря на похожее название.

## 6. Ошибки — два разных механизма

Это самое практически важное место во всей спеке.

**Ошибка протокола** — обычная ошибка JSON-RPC. Для: неизвестный инструмент,
некорректный запрос, поломка сервера.

```json
{ "jsonrpc": "2.0", "id": 3,
  "error": { "code": -32602, "message": "Unknown tool: invalid_tool_name" } }
```

**Ошибка выполнения** — успешный ответ с `isError: true`. Для: отказ внешнего API,
неверные аргументы по смыслу, нарушение бизнес-логики.

```json
{ "jsonrpc": "2.0", "id": 4,
  "result": {
    "content": [{ "type": "text",
      "text": "Invalid departure date: must be in the future. Current date is 08/08/2025." }],
    "isError": true } }
```

Разница в том, кто это чинит. Ошибку выполнения клиент **отдаёт модели**, и модель
может исправиться сама — поменять аргументы и позвать снова. Ошибку протокола модель
починить обычно не может.

**Отсюда прямое следствие для нашего инварианта 5:** «игра не найдена»,
«период пустой», «слишком много отзывов, сузь запрос» — это `isError: true`
с внятным текстом, а не ошибка JSON-RPC. Текст пишется для модели: он должен
говорить, что сделать дальше.

## 7. Уведомление об изменении списка

Если объявил `listChanged: true`:

```json
{ "jsonrpc": "2.0", "method": "notifications/tools/list_changed" }
```

Нам не нужно — список инструментов статичен.

## 8. Требования безопасности к серверу

Сервер **ОБЯЗАН**: проверять все входные данные, ограничивать частоту вызовов,
чистить вывод.

Клиент **СЛЕДУЕТ**: спрашивать подтверждение у человека на чувствительных
операциях, показывать аргументы до вызова, ставить таймауты.

Спека прямо говорит: аннотации и описания инструментов **недоверенные**, если сервер
не доверенный. У нас та же логика применяется на шаг глубже — недоверенным является
текст отзывов, который сервер возвращает.

## 9. Что делает SDK, а что пишешь ты

**SDK берёт на себя:** разбор и сборку JSON-RPC, разделение сообщений по строкам,
хендшейк, согласование версии, маршрутизацию `tools/list` и `tools/call`,
преобразование zod-схемы в JSON Schema.

**Ты пишешь:** регистрацию инструментов (`registerTool`), схемы аргументов на zod,
описания, обработчики, формирование `content`, решение об `isError`, логи в `stderr`.

Читать спеку всё равно надо: SDK прячет механику, но не решения. Что положить в
`description`, что считать ошибкой выполнения, а что протокольной, сколько
возвращать — за это отвечаешь ты.
